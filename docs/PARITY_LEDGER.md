# Feature Parity Ledger

This ledger states, feature by feature, where the Rust implementation stands
against the archived JavaScript release used as the behavioral oracle.

It is maintained by hand and checked by machine. `ty migrate check` classifies
a real project against the same vocabulary, and
`scripts/compat/differential.mjs` proves the "identical" claims by rendering
both implementations in a real browser and comparing what a user or an
assistive technology observes. Set `RELEASED_TY_BIN` to the checksum-verified
v26.30.04 executable; `TY_BIN` selects the Rust binary under test.

## How This Ledger Is Verified

Every row marked "Verified" was produced by running the real `ty` binary
against a minimal fixture in `scripts/compat/verify-ledger.sh`, not by reading
source. Run it with:

    ./scripts/compat/verify-ledger.sh

An earlier revision claimed component `tac.css` worked because page `tac.css`
worked. The component case actually failed until scoped component styles were
implemented and added to the executable verification harness. The row below
describes the current, executed behavior.

## Vocabulary

| Status | Meaning |
| --- | --- |
| `identical` | Both implementations accept the same authored source and produce the same observable result. Proven by the differential corpus. |
| `equivalent` | Both implementations support the feature and the observable result differs only in a way recorded here as intentional. |
| `changed` | Supported, but authored source must change. `ty migrate check` reports the required action. |
| `unsupported` | No Rust equivalent. The legacy implementation remains the only way to run it. |
| `rust-only` | A convention the Rust implementation introduces that the legacy implementation has no counterpart for. |

## View Layer

| Feature | Status | Notes |
| --- | --- | --- |
| `client/pages/**/tac.html` discovery and routing | `identical` | Corpus: `static-pages`, `semantic-html`. |
| **Dynamic route segments** (`_id`, `_version`) | `identical` | **Verified: implemented.** Discovery accepts `_name`, the route manifest carries ordered `parameters`, and nested segments compose (`/items/_id/reviews/_review`). A dynamic route is deliberately not prerendered, because its content depends on request-time values; the server renders it. Invalid or duplicated names fail with `TY1006`. |
| Semantic HTML: headings, `nav`, lists, links, images, rules, `details`/`summary`, tables, `footer` | `identical` | Corpus: `semantic-html`, two routes, byte-identical semantic DOM. |
| Standard HTML void elements (`<img>`, `<hr>`, `<br>`, `<input>`) | `rust-only` | The legacy parser rejects them with "No end tag." and requires the self-closing form. The Rust parser accepts both, so it is a strict superset. Corpus fixtures use the self-closing form so both can be compared. |
| Text interpolation `{name}` | `equivalent` | Both escape contextually. Context reaches the two implementations by different routes; see "Route context". |
| Dynamic attributes `:name="expr"` | `equivalent` | Same syntax, same escaping. |
| Conditionals `<logic :if>`, `<logic :else-if>`, `<logic else>`, `<if :when>`, `<else>` | `equivalent` | Resolved at compile time in Rust; the legacy implementation also resolves them at build time for prerendered pages. |
| Iteration `<loop :for>`, `<for :each>` | `equivalent` | Same syntax and bounds. |
| Tac components and `<slot>` | `equivalent` | **Intentional divergence:** the legacy implementation keeps the component as a runtime custom element (`<product-card>`); the Rust implementation expands it at compile time, so the component template's own root (`<article>`) reaches the document. Slotted content, accessible names, and roles are identical. Declared in `corpus/components-slots/parity.json`. |
| Conditional and arithmetic template expressions | `equivalent` | **Verified: implemented.** `condition ? a : b` and `+ - * /` are supported, so a template can pick a class inline (`slug === active ? 'active' : ''`) and build a path (`'/docs/' + topic.slug`), which is what the project's own website does throughout. `+` concatenates when either side is a string and adds otherwise; `*` and `/` bind tighter than `+` and `-`; division by zero is a missing value rather than an infinity, and a `null` alternative drops the attribute instead of printing `null`. The expression language stays bounded: no calls, no assignment, no side effects. |
| Companion fields inside an island | `equivalent` | **Verified in a real browser.** An island may read its companion's fields and call its methods: `{loadingState()}`, `{label}`, `{count + 1}`, `{report.rows.length}`, and `{await note()}` all resolve against the instance — evaluation is async there, so an awaited companion method works. The server resolves what it can and defers only what it cannot, so content that does not depend on the companion is still in the document before any script runs. Nothing is evaluated as source: the compiler emits the bounded AST it already parsed and the runtime interprets that fixed shape, the same approach event bindings use. See ADR 0010. |
| Released page class and literal `<script>` state | `equivalent` | **Verified in real Chromium and the native controller by `scripts/compat/standalone-rust.mjs`.** A plain page script may declare bounded literal state (`let count = 0`); a colocated default class supplies literal fields, methods, and `@onMount` lifecycle metadata. The compiler removes the script from HTML, creates one route-level island, emits its activation runtime even when there are no component islands, and produces the same state/controller behavior for web and native hosts. The browser clicks `count += 1` and observes `Count: 1`. Arbitrary inline expressions, attributes on the script tag, and executable initializers fail with `TY1306` rather than being evaluated. |
| Component fields outside an island | `unsupported` | A component with `hydrate="never"` has no client instance, so there is nothing to defer to and the build fails. Move the expression—not structural control flow—into an island or compute it in route context. |
| Method calls outside an island (`{loadingState()}`) | `unsupported` | A call invokes companion code, and a non-island component renders in Rust with no client instance to call. Method calls inside an explicit island or the released route-level page wrapper are equivalent. |
| `<switch>` / `<case :when>` / `<case default>` | `equivalent` | **Verified: implemented.** A switch is sugar for a conditional chain — `<case :when="a">` means `value == a`, first match wins, `<case default>` is the else — so it is desugared during parsing. The renderer, the native planner, and the view IR never learn a third control shape. The comparison node is built directly rather than by concatenating source, so a switch value like `a || b` cannot change meaning through operator precedence. A case after `default`, a non-`<case>` child, and an empty switch each fail with a diagnostic naming the rule. |
| Component `tac.ts` | `equivalent` | **Verified: implemented.** A TypeScript component companion is emitted through the TypeScript compiler itself, the same route a page companion takes, so its semantics are the reference semantics rather than a reimplementation. TypeScript 6 or newer is required, and a lower version fails with `TY1009` naming the version found. |
| Component `tac.css` | `equivalent` | **Verified: implemented, after failing silently for months.** A page-level `tac.css` worked while a component `tac.css` was rejected with `TY1401`, because `verify-ledger.sh` only ever probed the page case. Both are probed now. Styles are scoped with CSS `@scope`, the platform's own answer to component scoping: the compiler puts one `data-tac-scope` attribute on the component's root elements and emits `@scope ([data-tac-scope="<name>"]) { ... }` into `.tachyon/components.css`. Nothing parses or rewrites a selector, and no attribute is added per element the way `data-v-*` scoping requires. A browser without `@scope` ignores the block, leaving the component unstyled rather than leaking its rules. The stylesheet and its link are emitted only when a component has one. |
| Component path convention | `identical` | A component's directory names its tag at any depth: `clicker/` names `<clicker>`, `date-picker/` names `<date-picker>`, and `product/card/` names `<product-card>`. A tag without a hyphen is not a custom element name, but a component is compiled away rather than registered, so the collision that matters is with an element HTML has today — and a directory named for one is refused rather than silently changing what a template means. |
| Islands and `hydrate` policies | `equivalent` | Rust server-renders and activates by policy; proven against real Chromium in Phase 3. |
| `on:<event>` event bindings | `equivalent` | **Verified: implemented.** `on:click="increment()"` compiles to the `data-tac-on-click` marker, exactly as the legacy compiler does, and a delegated runtime calls the named export of the route's client module. Proven in real Chromium by `scripts/events-browser-test.mjs`: handlers with no arguments, with literal arguments, and receiving the event all fire. Binding values are parsed into a handler name and literal arguments and are **never** evaluated as JavaScript, so a view cannot introduce executable code. A route binding events without a client module fails with `TY1306`. |
| `tac.js` client module | `equivalent` | **Verified: implemented.** Emitted beside the route as `client.js` and referenced with `<script type="module">`. |
| `tac.ts` companion | `equivalent` | **Verified: implemented.** Emitted by the TypeScript compiler itself, so semantics are the reference semantics. Requires TypeScript 6 or newer at build time, which is the version that first accepts the emit flags — verified against 5.6, 5.9, 6.0.3 and 7.0.2. An older or absent compiler fails closed with `TY1009`. See ADR 0007. |
| Polyglot page companions (`tac.py`, `tac.rs`, `tac.kt`, `tac.swift`, `tac.cs`, `tac.dart`) | `unsupported` | **Verified: fails with `TY1008`.** A *page* companion is JavaScript or TypeScript. A *component* companion may be Rust, Dart, Kotlin, Swift, or C#, compiled to WebAssembly — see the browser-companion rows below. |
| General inline `<script>` in a view | `unsupported` | Executable inline code, imports, attributed scripts, and component/Yon scripts fail with `TY1306`. The one compatibility exception is the literal Tac page-state declaration described above. Behavior belongs in a client module or island. |
| Native `onclick=` attributes | `unsupported` | Verified: fails with `TY1306`, directing authors to `on:<event>`. This matches the legacy compiler, which also refuses to leave raw `on*` handlers in the DOM. |
| `$event` in an `on:<event>` binding | `equivalent` | **Verified in a real browser.** A binding may pass `$event` or a bounded dotted path off it, as in `on:input="setField('email', $event.target.value)"`. `$event` is the name Vue, Angular, and Alpine all converged on, and the one the project's own website already uses. The binding is parsed into a structure and emitted as JSON, never evaluated as JavaScript, so the no-script property holds: paths are plain identifiers, at most four segments deep. Proven by `scripts/events-browser-test.mjs` driving a real input. |
| Render-scope arguments in an `on:<event>` binding | `equivalent` | **Verified: implemented.** An argument may be a bounded template expression evaluated where the binding renders, so a loop passes the item it is iterating: `<loop :for="tab of tabs"><button on:click="select(tab.id)">` gives each row its own id. Without it a list of clickable rows cannot say which row was clicked. The expression is resolved at render time, not at click time, and the result is emitted as JSON the runtime reads — the authored expression never reaches the browser as source. Widening arguments from literals to expressions does not weaken the no-script property: `alert(document.cookie)` parses as a scope lookup of `document`, which is not in scope, so the build fails rather than the browser executing anything. |
| Assignment in an `on:<event>` binding | `equivalent` | **Verified in a real browser.** Inside an island a binding may assign to a field on the companion — `on:click="count += 1"`, `on:input="label = $event.target.value"` — and the island re-evaluates its own deferred expressions, so the rendered value follows. A binding also resolves its handler on the island's instance rather than the page module, so a component owns its behaviour and its state. This is not a reactivity graph: an island's expressions are a small fixed list known at build time, so re-running all of them is simpler and cheaper than dependency tracking. Assignment outside an island is refused, because there is no instance to write to. See ADR 0010. |
| `tac.css` / `yon.css` colocated styles | `identical` | **Verified: implemented.** Emitted beside the owning route as `style.css` and linked from the document. Reused routes keep them, and changing one invalidates its route. |

## Server Layer

| Feature | Status | Notes |
| --- | --- | --- |
| Request correlation identifiers | `identical` | **Verified:** dispatched requests carry a TTID, natively computed rather than spawned per request. Rust-generated ids match the v26.30.04 base-36 uppercase 100-nanosecond-tick contract and decode to their true creation time. |
| Route parameters delivered to handlers | `identical` | **Verified:** Handler Protocol v1 carries an optional `parameters` map, absent for a static route. |
| `server/routes/**/yon.js` handlers | `equivalent` | Rust supervises one bounded process per request under Handler Protocol v1. `GET()` may take zero parameters. |
| `server/routes/**/yon.py` handler signature | `changed` | **Verified:** Python's `GET` is invoked as `GET(request)` and must declare the parameter; the JavaScript adapter tolerates zero. |
| `server/routes/**/yon.py` handlers | `equivalent` | Same protocol and bounds. |
| Handlers in any other language | `equivalent` | **Verified: implemented, by a better route than the legacy takes.** The legacy ships a bespoke runner per language; this defines one direct protocol instead, so no per-language adapter exists at all. A handler reads one JSON request from stdin to end of file and writes one JSON response to stdout. Proven serving live routes from Ruby via `.tachyonrc` and from an executable POSIX shell script, and composing a build-time view context from Ruby. A handler is asked for its view context with `operation` set to `view.context` and answers with `{static_values, response_values}`; either may be omitted. An unregistered extension fails with `TY2003`, not `TY1008`, because the file is a valid handler that simply has no way to run. |
| `.tachyonrc` interpreter registration | `equivalent` | **Verified: implemented.** Maps a file extension to a bounded command. A handler with no registered interpreter that is executable runs directly; one that is neither fails with `TY2003` naming both remedies. |
| Handlers importing `server/services/**` or `server/repositories/**` | `unsupported` | Handler adapters do not import application modules. |
| `server/routes/**/yon.html` views | `rust-only` | The legacy implementation has no Yon view convention; it rejects `yon.html` as an invalid route handler. Composed route context is therefore a Rust-only capability with no legacy counterpart to compare against. |
| Route context from static handler fields and `GET()` | `rust-only` | Follows from the row above. |
| `middleware.js` | `equivalent` | **Verified: implemented for the `before` and `after` phases.** Root middleware is consulted before every request and speaks the same protocol a handler does, so it may be written in any language the project runs. A 204 continues; any other status answers the request without reaching the route. Proven refusing an unauthorised request in Ruby. The `after` phase receives the request headers plus the response status and headers under `x-tachyon-status` and `x-tachyon-response-*`; returning 204 merges its headers, any other status replaces the response, and an after-phase failure leaves the original response untouched. `headers` means request headers in both phases, so middleware reasons about the same request it authorised. The legacy `rateLimit` phase is deliberately not reproduced: returning 429 from `before` does the same job without a third phase. |
| `server/workers/**` background workers | `equivalent` | **Verified: implemented.** A worker is a handler invoked on a schedule instead of by a request, so it reuses the same protocol, supervisor, deadlines, and bounds, and may be written in any language. `.tachyonrc` declares the interval; paths must sit under `server/workers/` and intervals must be 1 to 86,400 seconds. A failed run is reported and the schedule continues, so one bad run never silently stops a recurring job. Proven with a Ruby worker running on a one-second interval. |
| HTTP handler dispatch | `equivalent` | **Verified: implemented.** The server matches a request path against the route graph, binds dynamic parameters, and invokes the supervised handler per request. Proven over a real socket in `crates/tachyon-core/tests/dispatch.rs`: parameter binding, percent-decoding, request bodies, multiple methods on one route, 405 for an unimplemented method, 404 for unknown paths, and traversal resistance. Production concerns such as pooling and keep-alive tuning remain open. |
| Realtime and topic logs | `equivalent` | **Verified: implemented, following the released protocol rather than replacing it.** The v26.30.04 design is an append-only NDJSON log per topic read by an integer-position cursor over server-sent events, so that contract is kept: a topic is `.tachyon/topics/<topic>.jsonl` and `GET /.tachyon/topics/<topic>` streams it as `text/event-stream`, each frame carrying its position as the event id. Publishing is appending a line, so a handler in any language publishes without a client library, and subscribing is `new EventSource(...)`, so the browser owns reconnection and resends its last id automatically. An explicit `?position=` is accepted for non-browser clients. Topic names are bounded slugs and a log over 16 MiB is refused. No WebSocket upgrade is implemented, because the released realtime surface does not use one. |
| Telemetry and OpenTelemetry spans | `out-of-scope` | **Excluded by an explicit product decision.** The archived v26.30.04 release emitted telemetry and the migration fixture records spans through an alert worker. The Rust implementation has no telemetry and will not gain it, so a project depending on emitted spans must instrument outside Tachyon or keep running the archived release. Structured request logging is a separate concern and is not covered by this row. `ty migrate check` reports a project-level unsupported finding when inspected source references telemetry; the signal is intentionally conservative and carries a manual migration action. |
| OpenAPI generation and `/api-docs` | `out-of-scope` | **Excluded by an explicit product decision, not because it is unused.** The archived v26.30.04 release serves OpenAPI 3.1 at `/openapi.json` and its documentation client at `/api-docs`. A project relying on those endpoints must keep running that release or generate a specification another way. Revisit if that trade is unwanted. |
| Every legacy command name (`init`, `serve`, `bundle`, `native-bundle`, `preview`, `cache`) | `identical` | **Verified by the released standalone workflow.** Existing command names, target aliases, target/environment selection, host and port environment variables, `YON_DIST_PATH`, `--no-bundle`, `--skip-package`, and one-or-many bundle targets are accepted. Removed whole-application render-mode inputs fail with an actionable native-first migration diagnostic. |
| `ty init` scaffold | `changed` | **Verified as an explicit migration against 26.30.04.** The differential requires 15 retained files to remain byte-identical, requires `.env.example`, `.env.test`, `README.md`, and `tachyon-env.d.ts` to differ after FYLO/telemetry cleanup, and requires the three legacy `db/` files to be absent. Any other difference fails the gate. |
| Legacy `OPTIONS.schema.json` request/response validation | `unsupported` | The Rust runtime does not discover or enforce this route-side schema. `ty migrate check` reports each file as `server.route_schema` with an action to validate in the handler or deployment boundary, or retain the archived server. |
| `ty cache status` / `ty cache clean` | `identical` | **Verified by the released standalone workflow.** The Rust binary preserves the released cache directory, `runtime/native-v1` entry, status wording, `TACHYON_CACHE_DIR`, and clean lifecycle even though its native runtime does not need JavaScript extraction. |
| Offline static cache | `equivalent` | **Verified in a real browser: the page loads with the network cut.** A service worker is generated at `/tachyon-sw.js`, which must be the root because a worker only controls pages at or below its own path. Navigations are network-first so a deployment is picked up at once, versioned static assets are cache-first, and caches from earlier builds are deleted on activation. The build digest is embedded in the worker's body rather than passed as `?v=`, because differing script bytes are already the platform's update trigger, so the registration URL never changes. Registration is skipped on a loopback host and any worker left there is unregistered, so a stale cache cannot fight live reload. Proven by `scripts/service-worker-browser-test.mjs`: the worker reaches the controlling state, the document and stylesheet are cached, and after `setOffline` the page renders with its styles applied and the server sees zero requests. |
| Component re-render registry | `out-of-scope` | **Superseded, not missing.** The released registry re-rendered one component subtree in place, which is only meaningful inside the client renderer that ADR 0009 deliberately does not reproduce. Components are composed at build time and verified as such, so there is no client-side render closure to register. A project needing in-place subtree updates uses an island. |
| `ty migrate check` accuracy | `equivalent` | **Verified: it runs the compiler instead of guessing.** The old file-name classifier once reported 142 supported, 1 changed, and 7 unsupported while the website build failed with 97 diagnostics. Views now use the real parser and its diagnostics become findings verbatim. After the website migration, the command reports 128 supported, 1 changed, and 1 unsupported, and the same sources build successfully. File- and project-level rules still cover what no view reveals. |

## Developer Loop

| Feature | Status | Notes |
| --- | --- | --- |
| Source watching and rebuild on change | `equivalent` | **Verified: implemented.** `ty dev` samples sources every 400 ms and rebuilds. A failed rebuild is reported and the previous output stays published, so a syntax error never takes the running site down. `--no-watch` disables it. |
| Live reload of an open page | `equivalent` | **Verified: implemented.** The server injects a same-origin reload client while serving, so `ty build` output never carries it. Proven in a real browser: editing a source reloads the open page with no console errors. |

| Single-page navigation | `changed` | **Deliberate divergence.** The client renderer is not reproduced. Every page instead opts into cross-document view transitions and prefetches same-origin routes through speculation rules, delivering instant and smooth navigation with no client renderer. State does not survive a navigation; hold it in an island, storage, or the server. See ADR 0009. |

## Native

| Feature | Status | Notes |
| --- | --- | --- |
| macOS, iOS, Linux, Windows, Android applications | `equivalent` | Both generate native applications. The implementations share no host source; per-platform evidence is in `PHASE_5_EVIDENCE.md` and tiers are in `SUPPORT_TIERS.md`. |
| Declarative HTML state contract | `changed` | Replaces arbitrary controller companions. |
| `ty doctor` | `rust-only` | Reports whether this machine has the toolchains a project needs, before anything is compiled: the TypeScript compiler for a `tac.ts`, every interpreter registered in `.tachyonrc`, and the per-language WebAssembly toolchain a polyglot browser companion will need. Only what a project actually uses is reported. `--json` emits the machine-readable form. **Each wasm toolchain is asked to build for its wasm target, not for its version**: every one of these languages ships wasm support separately from the compiler — a rustup target, a Swift SDK, a Kotlin standard library, a .NET workload — so `--version` answers happily on a machine that cannot build anything. Reporting presence rather than capability is what let four languages look ready when none of them were. The legacy implementation has no equivalent; it discovers a missing tool one build failure at a time. |
| Browser companion in Rust (`tac.rs`) | `equivalent` | **Verified in a real browser.** A `tac.rs` component companion is compiled by `rustc` to WebAssembly and loaded through the ABI in ADR 0011 — three exports, one JSON entry point, no bindgen and no glue crate. The island presents it as an ordinary instance, so deferred expressions, method calls, assignment and refresh all work unchanged: `{count}`, `{label}`, `{doubled()}` and `on:click="count += 1"` are proven against a Rust module in `scripts/wasm/companion-browser-test.mjs`. Emitted stripped at 21 KB. Compiled with edition 2021, the newest edition that does not require an author to spell `#[unsafe(no_mangle)]` on every export. |
| Browser companion in Dart (`tac.dart`) | `equivalent` | **Verified in a real browser**, in the same gate and against the same five assertions as Rust. Compiled by `dart compile wasm`, which emits WasmGC: the module exports 46 things and none of them is memory, imports 56, and `@pragma('wasm:export')` is refused in user code as internal — so it cannot satisfy the bare ABI and presents the glued shape instead, a module exporting `tacInvoke`. See the amendment to ADR 0011. 82 KB of wasm and 15 KB of the compiler's own loader, 98 KB in all. |
| Browser companion in Kotlin (`tac.kt`) | `equivalent` | **Verified in a real browser**, same gate, same assertions. Compiled by `kotlinc-js -Xwasm` in two passes, because the command-line compiler makes an executable only from a klib. Glued, like Dart: the module exports its memory but imports the JavaScript the compiler emits beside it. 120 KB with `-Xir-dce`, 584 KB without, so emission always passes it. Needs `kotlin-stdlib-wasm-js` from Maven Central in `KOTLIN_WASM_STDLIB`: `kotlinc` ships only the JavaScript standard library. |
| Browser companion in Swift (`tac.swift`) | `equivalent` | **Verified in a real browser**, same gate, same assertions. Compiled by the swift.org compiler against the Swift SDK for WebAssembly — Xcode's own `swiftc` cannot cross-compile to wasm and fails looking for `swift-autolink-extract`. Satisfies the bare ABI: `memory`, `tac_alloc`, `tac_invoke`, linked as a reactor so it exports `_initialize` rather than `_start`. Its 14 `wasi_snapshot_preview1` imports are answered by a do-nothing environment in the island runtime, because a WASI compiler emits them for a companion that performs no I/O. 5.5 MB stripped: Swift links its runtime and standard library, and Foundation would make it 53 MB, so the prelude scans the protocol's JSON itself. |
| Browser companion in C# (`tac.cs`) | `equivalent` | **Verified in a real browser**, same gate, same assertions. Published by the .NET SDK for `browser-wasm`, which needs the `wasm-tools` workload — a system-wide .NET needs elevated privileges to add it, a per-user one does not. Glued, and the heaviest of the five: the publish is not a module but a runtime, the companion's assemblies and a loader, 3.5 MB across 21 files, and the island's first value arrives after a runtime boot rather than an instantiation. The prelude builds its JSON by hand because `JsonSerializer` needs the reflection a trimmed publish removes. |
| A polyglot companion cannot satisfy both implementations at once | `changed` | **Measured, not assumed.** The legacy bundler refuses a Rust companion that declares imports ("Tac supplies its portable runtime APIs"), because it feeds a subset transpiler; a wasm companion is real Rust compiled by `rustc` and needs its `use` declarations. The same holds for all five languages: what the legacy build accepts is a subset, and what these compilers accept is the language. So an unmigrated project's companion targets one implementation or the other, and `ty migrate check` reports the rewrite it needs rather than as a wall. The website's five examples were migrated to their real compiler ABI on 2026-08-01 and now pass the five-language Chromium gate, so those companions are classified as `supported`; the website's sole remaining `changed` finding is `client.navigation`. |
| Capability Manifest v1 and Artifact Manifest v1 | `rust-only` | Versioned public contracts. |
| `WebSurface` subtree fallback with no bridge | `rust-only` | Unsupported subtrees fall back independently; supported siblings remain native. Local surfaces are CSP-constrained and remote surfaces disable JavaScript. Neither exposes a native bridge. |
| Same-origin navigation from a local `WebSurface` | `rust-only` | **Verified on the Android emulator.** A click on an `href`-bearing custom or web component leaves the surface and opens the matching native route. Physical taps drove the migrated website from `/` to `/docs` and then to the dynamic `/docs/introduction` route while the surrounding route stack stayed native. |
| Custom design-system native adapters | `rust-only` | **Verified: semantic, not tag-specific.** A custom element reaches a native adapter through an explicit HTML/ARIA role such as `role="banner"`; unknown elements without a supported role remain bounded `WebSurface` subtrees. The planner contains no DuVay `w-*` tag names. |

## What the Ledger Does Not Claim

- No row claims that a Rust feature is production-ready. Readiness is governed
  by `SUPPORT_TIERS.md`.
- `unsupported` never means "will not be supported". It means there is no Rust
  equivalent today and the archived release is still required.
